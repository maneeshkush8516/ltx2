# 30+ improvements to LTX.PY video generation notebook

A substantial expansion of a single-file Colab notebook for AI video generation, adding dataclass-based config, generate_clip decomposition into sub-functions, CLIP conditioning caching, graduated OOM retry, checkpoint/resume, character bible drift detection, latent-space slerp blending, camera LoRA auto-selection, Google Drive sync, per-beat transitions, adaptive sigma scheduling, prompt caching, seed exploration, and dynamic frame counts. The original 1587-line file grows to 3753 lines with the same cell structure preserved.

**Watch for:** Node-name typo in the latent_slerp path (`LTXVConcatLatentAV` vs `LTXVConcatAVLatent`) will crash that code path at runtime (confirmed). CLIP conditioning cache stores references to GPU tensors while documenting "on CPU" -- will silently consume VRAM across clips (confirmed). Audio continuity's `_generate_audio_for_full_video` is a stub that never actually merges audio with the video (confirmed). ThreadPoolExecutor-based timeout cannot interrupt GPU kernels so the timeout is advisory at best (likely).

## High-level view

The core refactoring splits `generate_clip`'s monolithic body into `_load_clip_encode`, `_load_unet`, `_prepare_latents`, `_pass1`, `_preview`, `_pass2`, `_decode_video`, `_decode_audio`, and `_save`. Each function is well-scoped and the node instance cache (`_NODE_INSTANCES`) avoids redundant instantiation. However, several new sub-systems interact poorly under VRAM pressure: the CLIP cache accumulates GPU tensors indefinitely until `_clear_clip_cache()` is explicitly called, and the TinyVAE persistent model adds another ~50MB resident object to a T4 that's already at 13GB peak.

The `latent_slerp` blending path has a confirmed typo (`LTXVConcatLatentAV` instead of `LTXVConcatAVLatent`) that will raise `KeyError` at runtime. This path also encodes two images through VAE, slerps, decodes back to pixel space, then feeds through `LTXVImgToVideoInplace` -- a round-trip that loses the precision benefit of operating in latent space.

Audio continuity (`skip_audio=True` per segment, then post-hoc audio generation) has a plausible design but `_generate_audio_for_full_video` never completes the ffmpeg merge step: it generates an audio latent, decodes it, then returns the original silent video path unchanged. The method is effectively a no-op.

The graduated OOM retry and per-clip timeout via `ThreadPoolExecutor` are architecturally sound as degradation ladders, but the timeout mechanism cannot actually interrupt a blocked CUDA kernel -- the future will only complete when the GPU releases. On a T4, a stuck kernel can hold the thread indefinitely.

The drift detection system (VisionDescribe on current frame, regex attribute comparison against bible) is creative but loads a 3B vision model mid-generation. When `drift_check_interval > 0` and `keep_loaded=False`, this means a multi-GB model load/unload every N beats, which on a T4 may itself trigger OOM in the window between UNet unload and VAE decode.

## Node-name typo in latent_slerp path

In the `latent_slerp` branch of `generate_clip` (line 2425), the code references `_get_node("LTXVConcatLatentAV")`:

```python
clat_sl = _get_node("LTXVConcatLatentAV")
av_lat = get_value_at_index(
    clat_sl.EXECUTE_NORMALIZED(
        video_latent=get_value_at_index(vid_lat_sl_result, 0),
        audio_latent=get_value_at_index(aud_lat_sl, 0)), 0)
```

Every other call site and the `_populate_node_instances` cache use `"LTXVConcatAVLatent"`. The `_get_node` fallback will attempt `NODE_CLASS_MAPPINGS["LTXVConcatLatentAV"]()` which will raise `KeyError`. Since `blend_mode` defaults to `"pixel"`, this only triggers when explicitly requested -- but when it does, it crashes.

## CLIP conditioning cache does not move tensors to CPU

The docstring says "stores results in cache (on CPU) for future reuse" but the implementation stores the raw `cond` tuple returned by `LTXVConditioning`:

```python
_CLIP_COND_CACHE[prompt] = {"cond_result": cond, "cond_pos": None, "cond_neg": None}
```

The `cond` tuple contains tensors allocated on CUDA. There's no `.cpu()` call before caching. With each unique prompt, conditioning tensors (~200-500MB depending on sequence length) accumulate on the GPU. The `device` variable computed on cache hit and the `cond_pos_cached` / `cond_neg_cached` assignments are dead code -- the function returns `cached["cond_result"]` directly without using them.

## Audio continuity stub

The `_generate_audio_for_full_video` method:

1. Loads audio VAE
2. Gets frame count from video via OpenCV
3. Generates `LTXVEmptyLatentAudio` for full duration
4. Decodes audio latent via `LTXVAudioVAEDecode`
5. Returns `video_path` unchanged

The comments say "Save audio tensor as wav (simplified -- actual implementation depends on ComfyUI audio format)" and "Use ffmpeg to combine" but neither step is implemented. The decoded audio tensor is silently discarded.

## Timeout mechanism and GPU kernel blocking

```python
executor = ThreadPoolExecutor(max_workers=1)
future = executor.submit(generate_clip, image_tensor=image_tensor, **base_kwargs)
try:
    result = future.result(timeout=self.clip_timeout_sec)
except FuturesTimeoutError:
    raise ClipTimeoutError(...)
finally:
    executor.shutdown(wait=False)
```

When the timeout fires, the worker thread continues running the CUDA kernel. `executor.shutdown(wait=False)` does not terminate it. The subsequent retry competes with the orphaned computation for GPU memory, potentially cascading into OOM.

## Transition filter construction produces identical output for crossfade and dip_to_black

```python
xfade_mode = "fade" if transition_type == "crossfade" else "fade"
xfade_color = "" if transition_type == "crossfade" else ":color=black"
```

Neither variable is used in the filter string construction. Both types produce `xfade=transition=fade:duration=...`. For `dip_to_black`, the ffmpeg xfade filter should use `transition=fadeblack` or append the color parameter to the filter.

The audio crossfade path (`acrossfade`) does not verify inputs have audio streams. Clips generated with `skip_audio=True` have no audio stream, causing ffmpeg to fail on `[N:a]` reference and triggering hard_cut fallback.

## LoRA stack mutation during generation

```python
# Inject
for i, slot in enumerate(LD_LORA_STACK):
    if not slot.on:
        LD_LORA_STACK[i] = camera_lora
        injected = True
        break

# ... generation happens here (can throw) ...

# Restore
if orig_lora_stack is not None:
    LD_LORA_STACK[:] = orig_lora_stack
```

If `_generate_single_segment` raises (e.g., all OOM retry steps exhausted), the global `LD_LORA_STACK` retains the injected camera LoRA for all subsequent beats. Wrapping in try/finally would make this safe.

## Checkpoint config hash is too narrow

```python
cfg_str = f"{self.width}:{self.height}:{self.frames}:{self.fps}:{self.mode}"
cfg_hash = hashlib.md5(cfg_str.encode()).hexdigest()[:12]
```

A user changing `creativity`, `image_strength`, LoRA configuration, the story beats list, or `extensions_per_clip` will not invalidate the checkpoint. The resumed generation will use new settings but start from intermediate state produced under old settings.
